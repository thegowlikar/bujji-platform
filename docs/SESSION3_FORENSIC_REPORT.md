## 3. Watchdog Behaviour

The single most important piece of evidence from today: **the first live exercise of the P1 `TickSilenceWatchdog`/`force_reconnect()` fix under a real recurrence of the original failure signature**, not a fault-injection simulation.

Exact sequence (from `logs/live_shadow_session_s3.log`):
```
09:15:00.271  tick_silence_detected        (market_hours gate activates; tick_age already ~6742s)
09:15:01.271  tick_feed_force_reconnect    (single reconnect issued, per design)
09:15:01.403  Websocket connected          (132ms handshake)
09:15:03.273  tick_feed_connected          (on_connect closure completes)
09:15:03.274  tick_silence_detected        (correctly re-flags: is_connected=True again, but still no FRESH tick)
09:15:04.275  tick_silence_watchdog_recovered   (a real fresh tick had arrived — only then declared recovered)
```
Total: **4.0 seconds from detection to recovery, fully automatic, zero operator intervention, exactly one reconnect issued** (no storm). The intermediate re-detection at 09:15:03.274 is not an anomaly — it is the watchdog correctly declining to call a bare reconnect "recovered" without evidence of an actual fresh tick, which is precisely the design intent verified synthetically in the P2 fault-injection harness (Scenario 3). Today is the first time this exact logic path executed against real market data and a real SDK.

**Watchdog interventions today: 1. Reconnect attempts: 1. Max backoff reached: no. CRITICAL_FAILURE: never reached (0 occurrences).**

Separately, the 07:47 Cloudflare burst produced **zero** watchdog-issued reconnects — consistent with, and now live-confirming, the P2 fault-injection finding that Cloudflare-style flapping is absorbed entirely by the SDK's own internal reconnect path while the watchdog's `is_connected`-gated activation rule correctly stays out of the way.
